# 已知明文推导法（卡密算法还原首选路线）

> 融合来源：`r0crawl_skills` 的 KCTF2026 题解方法论（五步推导法）+ `ctf-key-recovery`
> 的 verifier 检查清单。本文件已按**卡密/授权码场景**重写，并补入实测踩到的两个真坑。
> 配套工具：`scripts/derive_block_solver.py`（已用原题 KCTF2026 第 7 题 4 组样例 +
> FLAG 密文端到端实测：`python scripts/derive_block_solver.py --selftest` → PASS）。

## 一、什么时候走这条线（S0 判定）

**触发条件：手上有一枚能通过验证的有效卡密样本**（或试用码、或目标自带的已知明文对）。

这是卡密算法还原的最强前提：
- 校验算法若**无密钥熵**（自定义编码/打乱/固定偏移），**已知明文足以唯一反推全部参数**；
- 不必猜算法（不要一上来就猜 AES/MD5）、不必爆破、不必硬啃混淆代码；
- 对 **OLLVM / VMP 目标尤其值**：静态读不出逻辑时，用「已知卡密 → 机器码/注册码」样本对直接反推。

**不适用的信号**（立刻转 `crypto-signature-playbook.md` 的标准算法识别路线）：
- 去掉块结构后与明文等长、且无固定骨架 → 可能只是简单 XOR/Base64；
- 密文长度不等于块大小整数倍；
- 明显是标准算法（AES/RSA/RC4/SM4 常量在二进制里能找到）。

## 二、五步推导法

### 步骤 1：定块结构 —— 找骨架，分离有效位
把多组密文按块对齐，逐半字节比较：
- **所有块都相同的半字节** → 骨架（固定模板，无信息）；
- **随明文变化的半字节** → 有效数据位。

> 技巧：用同族、**明文差异大**的样本（比如 1 字节 vs 5 字节 vs 3 字节）才能暴露全部有效位。

### 步骤 2：定分块 —— 明文怎么切
- 块数 == `ceil(len(明文) / N)`，反推 N；
- **块序方向**（最容易搞反）：改明文第 1 字节，看哪个密文块变 → 定位方向。
  常见约定是「从右往左分块、块序从右往左」→ **尾块出现在密文最后**。

### 步骤 3：定变换 —— 反推两个半字节偏移
对单字节样本反推：把明文字节拆 (H, L)，密文有效对 (a, b)，则
```
(a, b) = (L+pL, H+pH)   或   (H+pH, L+pL)
```
两种只差**先后顺序**，偏移是同一对 (pL, pH)。用多样例求交即可定出唯一 (pL, pH)。

> **每个字节用哪种顺序由「密钥序列」决定**：常见是周期循环（如 1,2,1 表示
> 交换/不交换/交换）。密钥可能按**块内字节序**推进，也可能按**明文全局字节序**推进——
> 两者在 `chunk % period == 0` 时不可区分，工具会同时搜索并报最短周期解。

### 步骤 4：定重排 —— 块内字节顺序
比较「明文块内顺序」与「有效位顺序」：常见是循环移位（`ABC -> CAB` = 右循环 1）或反转
（两字节块 `AB -> BA`）。**每种块长（含尾块）可能不同，必须分别定。**

### 步骤 5：定尾块 —— `len % N` 决定特殊结构
**尾块的有效位位置与完整块不同，必须单独 probe**，不能复用完整块的位表。

## 三、工具：`scripts/derive_block_solver.py`

```bash
# 样例 JSON：[{"plain": "有效卡密", "cipher": "它生成的密文hex"}, ...]
python scripts/derive_block_solver.py --samples samples.json --block-size 6 --chunk 3
# 顺带解目标密文并断言
python scripts/derive_block_solver.py --samples s.json --decrypt <hex> --expect '<期望明文>'
# 自检工具本身（KCTF2026 第 7 题，模型与卡密完全同构）
python scripts/derive_block_solver.py --selftest
```

输出：骨架位 / 有效位位置 / 每字节偏移 (pL,pH) / 密钥序列（周期 + 槽位）/ 块序 / 重排，
并直接给出样例回代与目标密文解密。**多解时会全部列出并按最短周期 + 可打印性排序**。

搜索范围可用 `--max-period` / `--block-size` / `--chunk` 调整；若报「没有自洽解」，
先核对块大小与 chunk，再考虑是否属于标准密码学算法。

## 四、实测踩过的坑（重点）

| 坑 | 现象 | 解法 |
|---|---|---|
| **单块伪解污染全局参数** | 只有 1 个观测的块（如 1 字节尾块）能被**任意** (位置,偏移) 组合解释，这些伪解会把真正一致的参数挤掉 | 建模时把「两种顺序」写成**同一对偏移 + 顺序标记**，而不是两套独立偏移；否则跨块长的一致性检查必被伪解破坏 |
| **把未知长度的尾块当完整块** | 拿待解密密文的最后一块当完整块喂给骨架判定 → 骨干集被污染，全部候选被否 | 骨架判定只用**已知明文的样本块**；待解密文只贡献「非末块」作为完整块证据 |
| 块序搞反 | 明文整体逆序 / 只有首尾块错 | 改明文第 1 字节看哪个密文块变 |
| 密钥流对齐错 | 每块第 1 字节错 | 密钥是按字节**全局连续**推进，不是每块重置（除非周期与块长整除，看不出差别） |
| 尾块当完整块 | 尾块字节全错 | 尾块有效位位置独立，按 `len % N` 单独 probe |
| 骨架位置算错 | 半字节取错 | 半字节索引 = `字节序号*2 + (0=高 / 1=低)`，别搞反 |
| 重排方向错 | 块内字节顺序错 | 加密右循环 → 解密左循环，别用反 |
| 复用老版本参数 | 新版本改了算法 | 换版本必须重跑推导（参见 SKILL.md §1.3b 老办法不保证适用） |

## 五、Verifier 检查清单（声明成功前逐项过）

来自 `ctf-key-recovery`，按卡密语境改写：

- [ ] 进入校验的**确切字节**是什么（是否去空格 / 大写化 / 带前缀）？
- [ ] 是否先检查卡密长度再编码？
- [ ] 编码方式（UTF-8 / GBK / Base64）是哪一种？
- [ ] 哪个常量只影响**显示**、哪个常量真正参与**比较**？（别把显示常量当判定常量）
- [ ] 循环用 `i % key_len`、固定周期，还是状态反馈？
- [ ] 代码字节与常量字节是否分别变换？
- [ ] 成功是否需要**执行还原出的代码**，还是只做字节比较？
- [ ] **推导出的参数解所有已知样例是否 100% 通过**？
- [ ] 目标密文解出后是否**可打印且符合格式**（多解时以此判定）？
- [ ] 真实程序是否接受还原出的明文/卡密（有条件就实测）？

## 六、验收（三条全过才算完成）

1. **样例全过**：推得的解密器能 100% 还原全部已知样例；
2. **目标可读**：解出的目标密文可打印、符合目标格式；个别字节错 → 回头查尾块与密钥对齐；
3. **唯一自洽**：自洽解不唯一时，必须给出判据（最短周期 + 可打印性）说明为何选它，并
   把其它解的差异写进报告（对应 SKILL.md 的 E# 台账纪律）。

> 与 `references/crypto-signature-playbook.md` 的分工：本文件负责「已知明文反推自定义编码」，
> 该文件负责「加密原语识别（XTEA/RC4变体/SM4/CRC64…）」与签名参数攻坚。两者互补。
