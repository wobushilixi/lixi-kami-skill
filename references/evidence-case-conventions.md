# 证据工程与案件目录约定（融合自 r0crawl_skills）

> 目的：把「我感觉这里是加密」推进到「我有证据证明输入、变换、输出与复现结果」。
> 与 SKILL.md 的 E# 假设台账、DoD 交付门槛、`failure-taxonomy.md` 失败台账配套使用。

---

## 一、目录约定（与现有 `work/`、`cases/` 并存）

```
work/<目标名>/                # S1 侦察产物（s1_recon.py 自动生成）
  recon.md  recon.json  decomp/*.c  ...
cases/<目标名>/               # 案件主目录（本文件约定的对象）
  case.yaml                   # 目标身份：size / SHA256 / 类型 / 版本 / 目标产物
  evidence/raw/               # 原始证据，只读：样本、HAR、PCAP、logcat、maps、内存片段
  evidence/derived/           # 派生产物：dump、反编译输出、解密串、补丁后样本
  notes/timeline.md           # 时间线：做了什么 → 观察到什么（对应哪条 E#）
  notes/hypotheses.md         # E# 假设台账
  repro/                      # 复现脚本与命令（能一键重跑）
  tests/fixtures.jsonl        # parity 夹具（输入 → 期望输出）
  manifest.json               # 产物清单：地址/大小/来源/SHA256/工具版本
  failures.tsv                # 失败台账（F 编号，见 failure-taxonomy.md）
  report.md                   # 交付报告（模板见下）
```

一键建目录：`python scripts/init_case.py <目标名>`（生成骨架 + E# 模板 + failures.tsv）。

**铁律**：`evidence/raw/` 只读——任何解码、patch、dump 都写到 `derived/`，原始件永不改动。

## 二、产物清单 `manifest.json`（每个交付物都要有）

| 字段 | 含义 |
|---|---|
| `name` | 产物名（补丁后的 APK / dump 出的 dex / 还原的算法脚本） |
| `origin` | 来自哪一步（E# 编号 / 内存地址 / 文件偏移 / 请求） |
| `size` | 字节数 |
| `sha256` | 摘要（`hash_artifact.py` 或 `python -c` 算） |
| `tool` + `tool_version` | 用什么工具产出（IDA 9.3 / jadx 1.5.5 / Unicorn …） |
| `validated_by` | 用哪个**消费工具**验证过（jadx 能打开 / IDA 能反编译 / 真机装上） |

> **不要拿「字符串命中」或「单条日志」当已确认的调用链**；dump 出来的产物在
> **消费工具能正常加载**之前，不算有效产物（对齐 SKILL.md 的置信度分级）。

## 三、Parity 夹具与差分（签名/算法还原的验收核心）

**夹具格式**（`tests/fixtures.jsonl`，每行一条，一次只改一个输入）：

```json
{"name":"base","input":"...","expect":"..."}
{"name":"ts_changed","input":"...","expect":"..."}
```

差分：`python scripts/parity_diff.py tests/fixtures.jsonl out/result.jsonl --ignore ts,nonce`

判定标准（逐档，别跳档）：
1. **本地实现能复现第一条夹具**；
2. **全部夹具一致**——不一致时打印首个差异字段（这才是有价值的失败信息）；
3. **与真实环境一致**：本地结果 == 浏览器/真机实际发出的请求（→ 用真实请求验证，不看本地自嗨）；
4. **跨版本抽查**：目标换版本后重跑夹具（老办法不保证适用，见 SKILL.md §1.3b）。

`--ignore` 用来排除时间戳、随机数、nonce 这类**本来就该变**的字段——不排除它们，
parity 永远不可能一致，也永远发现不了真正的差异。

## 四、稳定性回归清单（下结论「补丁稳定 / hook 稳定」前）

| 检查 | 为什么 |
|---|---|
| 干净基线（未打补丁）记录原行为 | 没有「复现为红」，无法证明补丁起了作用 |
| **冷启动**（杀进程重开） | 只测热启动会漏掉初始化期的一次性判定 |
| **热启动 / 重复运行 ≥3 次** | 一次性成功的补丁常在第二次运行时失效（计数器、缓存、心跳） |
| 边界输入（空 / 超长 / 非 ASCII） | 校验分支常在这些输入上走另一条路 |
| 版本回归 | 换版本重跑，不套用上次的补丁点 |

> 只跑一次就说「稳定」= 未验证。对应 DoD 第 5 条与置信度分级。

## 五、报告模板（`report.md`）

```markdown
# <目标> 分析报告

## 一句话结论
（大白话：能不能绕过 / 卡在哪 / 需要什么才能确定）

## 目标身份
name / size / SHA256 / 类型 / 版本 / 获取来源

## 保护与对抗层
壳（类型 + 置信度 + 证据）｜签名校验｜反调试｜环境检测｜结论：影响哪一步

## 证据
| # | 证据 | 来源（文件:行 / 地址 / 请求） | 支持哪条 E# | 状态（证实/推翻/未知） |

## 技术链路
入口 → 加载/解密 → 判定 → 放行/拦截（哪一层改的、为什么改这里能放行）

## 复现
命令 / 脚本 / 夹具（能一键重跑）

## 局限与未验证项
真机未测？无有效样本？只覆盖某一版本？（必须如实写）

## 下一步
具体到「需要什么输入 / 跑哪条命令 / 看哪条输出」
```

## 六、与 DoD 的映射

| DoD 条目 | 本文件对应证据 |
|---|---|
| ① 目标已确认 | `case.yaml` 的 size+SHA256+类型 |
| ② 保护分析完成 | 报告「保护与对抗层」节 |
| ③ 判定点有直接证据 | 报告证据表 + `manifest.json` 的 `validated_by` |
| ④ 产物过自检 | `verify_patch.py` / `zipalign4.py check` 输出入库 |
| ⑤ 验证证据充分 | 夹具 parity + 稳定性回归（或 S4 三条闭环） |
| ⑥ 残留风险已列 | 报告「局限与未验证项」 |
| ⑦ 无未验证猜测当结论 | E# 台账全部结算（证实/推翻/仍未知） |
