# S0 可破性分诊：动手前 10 分钟判定「能不能打、怎么打、什么时候停」

> **为什么要有这一步**：实战成功率的杀手不是"技术不够"，而是**在不可达的目标上按可达目标的流程打**——
> 没有有效样本却去还原算法、纯服务端判定却去 patch 客户端、强壳加完整性却按无壳路线做。
> 打之前花 10 分钟分诊，能挡掉一大半"注定失败"的工时，剩下的目标命中率自然高。

分诊结论写入《分析报告》第一节，格式见文末模板。

---

## 一、五个问题（Q1–Q5）

### Q1 有没有「有效样本」？

一个**能正常通过验证**的卡密 / 账号 / 试用入口 / 已激活的旧版本，是整条链路里最贵的资源。

| 回答 | 含义 |
|---|---|
| 有 | 可做协议对比、算法验证、keygen 可验证；适用全部路线 |
| 只有试用 | D 类路线可用；到期/计数逻辑可对比 |
| 没有任何有效输入 | **keygen 路线不可验证 → 不作为主路线**；只能走「让无效输入通过」的 patch / mock / 仿真路线（见 Q2、Q4） |

**没有样本时唯一合法的验证方式是**：unicorn 离线仿真（`references/unicorn-emu.md`）或 mock 联调——用"改完之后无效输入能过"作为判据，而不是"生成的码能被接受"。

### Q2 判定位置在客户端能不能拿到？

| 架构 | 判定点位置 | 客户端可改? |
|---|---|---|
| A 纯本地算法 | 客户端 | ✅ 可 patch / 可仿真 / 可 keygen |
| B 本地+服务端 | 客户端解析响应后的判定分支 | ✅ 改判定分支（比伪造响应稳） |
| C 服务端主导 | 服务端；客户端只有结果展示 | ⚠️ 只有「改解析后判定 / mock 响应」两条路，服务端一改就白干 |
| D 试用/计数 | 客户端计时/计数 | ✅ 冻结/重置 + 配套反回退 |

**判定位置不明的处理**：跑「断网一次、抓包一次、清本地存储一次」三态对比，不许凭感觉归类。

### Q3 可改造性（重打包这条路通不通）？

| 信号 | 影响 |
|---|---|
| 有签名自校验 / 完整性校验（Dex CRC、APK hash） | 重打包路线成本 +1；先评估 MT/NP 一键去签是否够用 |
| 有环境检测（root/模拟器/反作弊 SDK） | 补丁生效 ≠ 能用；必须过 `android-env-detection.md` |
| 只有运行时可行（强壳、so 内存加载、VMP） | 放弃重打包，走运行时 / 仿真 / mock |
| Web 前端 | 无此问题，改 Overrides 即可 |

### Q4 动态能力（决定"怎么验证"）

| 条件 | 能力 |
|---|---|
| 有 root 真机 | 全套动态（maps dump / gdbserver / LSPosed）；最高验证强度 |
| 只有普通手机/模拟器 | 安装 + logcat 可用；so 层动态不可用 |
| **无设备（纯静态环境）** | ① 纯 Java 层：模拟器验证（x86_64 AVD 可跑无 arm so 的包）② 本地算法：**unicorn 离线仿真**（一等功能，见 `unicorn-emu.md`）③ 其余：S4 三条闭环收口 + 如实标注 |

**Frida 在本机安卓端不可用**（skill 既定约束），无设备时的动态替代就是 unicorn / 模拟器 / qemu。

### Q5 家族已知度（有没有"现成打法"）

| 命中 | 直接跳转 |
|---|---|
| 已知网络验证 SDK（天御/易游/飘零/飞扬/至简/索玛等） | `network-sdk-fingerprints.md`，按家族打法走 |
| 已知壳（腾讯乐固/爱加密/梆梆/娜迦/顶象/几维 等） | `packer-analysis.md` + `unpack-repack.md` |
| 已知开源卡密系统（卡密宝、独角数卡、异次元发卡、彩虹等） | `open-source-mapping.md` O1：拉源码对照定位 |
| 与上一次做过的目标同族/同作者 | 先跑 `1.3b 类级 diff`，老办法要重新验证 |
| 全都不认识 | 按通用流程走，同时把新指纹登记进家族表（`network-sdk-fingerprints.md` 末尾） |

## 二、分诊结论 → 路线与预期档位

| 组合 | 推荐路线 | 预期档位 | 最大风险 |
|---|---|---|---|
| A/D + 无强壳 + 有/无样本 | smali/so patch 或算法还原；无样本可加 unicorn 仿真 | **高** | 判定点漏枚举 |
| B 类 + 判定分支可定位 | 改解析后判定分支 + 本地缓存 | **高** | 到期后心跳纠正 |
| 已知 SDK / 已知壳 | 按家族既定打法 | **中–高** | SDK 魔改 |
| Unity IL2CPP / Flutter | Dumper 还原符号后 patch | **中** | metadata 加密 |
| C 类 + 响应无签名 + 无强壳 | mock server / hosts + 改判定 | **中** | 服务端协议变动 |
| C 类 + 响应签名 + 完整性校验 | 改客户端判定（不伪造响应） | **低–中** | 多处判定 + 心跳 |
| 强壳 + VMP + 完整性强校验 | 运行时路线为主 | **低** | 脱壳/内存 dump 失败即停 |
| 纯服务端算法 + 无有效样本 + 无客户端判定 | **不可达（客户端路线）** | — | 别打，立刻转替代输出 |

写结论时必须用**档位 + 依据**，不写"应该可以"这类模糊话。

## 三、判为「不可达」时的四个替代输出（不等于失败）

1. **向用户要一个有效样本**（能过验证的卡密/账号/旧版激活态）→ 拿到后重新分诊，多数会跳到"中/高"。
2. **要服务端视角**（授权范围内的后台/内网/服务器凭据）→ 转 `network-pentest`，从服务端拿判定权。
3. **换攻击面**：本地缓存文件伪造、UI 层展示、试用重置、环境检测绕过——这些不需要有效样本。
4. **诚实终止**：交付《分诊报告》+ 已排除的攻击面 + 需要的输入；并登记失败台账（F 编号，见 `failure-taxonomy.md`）。

> 把不可达目标挡在 S1 之前，是提高成功率的主要方式之一：**成功率 = 成功数 / 尝试数，减少注定失败的尝试数比硬啃更有效**。

## 四、止损线（时间盒，防止一条路磨到死）

| 检查点 | 默认线 | 到线动作 |
|---|---|---|
| S1 找不到任何候选判定点 | 预算的 25% | 升级动态：抓包 / logcat / 仿真 / 内存 dump，而不是继续 grep |
| 连续 2 次无证据支撑的失败 | 立即 | 强制回 S1（skill 既有硬规则），并复核 Q2/Q4 是否判错 |
| patch 后闪退 ≥2 次 | 立即 | 走 `crash-troubleshooting.md`，禁止继续盲改 |
| 同一层改了 3 处仍无效 | 立即 | 换层：Java→native→网络→仿真，不要在第 4 处继续 |
| 目标是"每次都要重新打"的心跳型 | 出现即 | 从 patch 判定改为 patch 解析后判定 + 本地缓存，或上 mock |
