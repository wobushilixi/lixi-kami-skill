# 失败台账：把"成功率低"变成可统计、可整改的清单

> 成功率不会因为"更努力"而提高，只会因为**知道失败集中在哪**而提高。
> 规则：每次任务（成功的也要）在案例目录记一行；每 5 个案例统计一次分布；
> **频次最高的 F 编号必须转成 skill 的具体改动**（补脚本 / 补文档 / 改流程），否则台账无效。

## 一、失败分类（F 编号）

| F | 名称 | 典型症状 | 直接对应的兜底资产 |
|---|---|---|---|
| F1 | 壳/混淆超预算 | 脱不出来、OLLVM 平坦化读不动 | `packer-analysis.md`、`unpack-repack.md` |
| F2 | 判定点定位失败/漏枚举 | 改了没用、界面仍显示未激活 | `bypass-playbook.md` §7.1、`kami_scan.py` |
| F3 | 签名/完整性校验 | 装不上、秒退、无日志自杀 | `crash-troubleshooting.md` §2、MT/NP 一键去签 |
| F4 | 环境检测/反作弊 | 补丁生效但被拦、闪退在检测点 | `android-env-detection.md` |
| F5 | 联网后失效 | 断网能用联网又被纠正 | `network-sdk-fingerprints.md`（改②/④打点） |
| F6 | 无有效样本 | 算法还原无法验证、keygen 不可信 | `feasibility-triage.md` Q1 |
| F7 | **工具链/操作性失败** | 对齐、签名顺序、中文路径、回编报错 | **`s4_pipeline.py`（一条命令固化顺序）** |
| F8 | 动态能力缺失 | 无设备/无 Frida，只能静态推断 | **`unicorn-emu.md`（离线仿真）**、模拟器 |
| F9 | 目标不可达 | 纯服务端判定 + 无客户端判定点 | `feasibility-triage.md` §三（转替代输出） |
| F10 | 版本/需求变化 | 换新版后老补丁失效 | `SKILL.md` §1.3b（类级 diff） |

**F7 / F8 已被本版新增工具直接覆盖**——若这两类还在高频，说明流程没走 `s4_pipeline.py` / `emu_check.py`，是执行问题不是能力问题。

## 二、记录格式（案例目录 `cases/<目标名>/failures.tsv`）

```
日期	目标	家族/壳	F	一句话根因	整改动作
2026-10-08	libcardverify.so	未知(跨库sret)	F8	缺辅助库符号 L__0x9Qq，仿真到边界	已记入 unicorn-emu.md 局限表；下次先查 --dep 是否可补
```

## 三、回看规则（每 5 个案例）

1. 统计 F 分布，写出前三名；
2. 对第一名给出**具体整改**：能脚本化的补脚本、能模板化的补 reference、纯流程的写进 SKILL.md；
3. 整改完成前不开始同类型新案例（防止在同一个坑里连续摔）。

## 四、和既有纪律的衔接

- 本台账不替代 E# 假设台账：E# 管"单次任务内的假设-验证"，F 台账管"跨任务的失败分布"。
- 失败不等于白干：把"已排除的攻击面 + 需要的输入"写进交付（`feasibility-triage.md` §三），也是有效产出。
