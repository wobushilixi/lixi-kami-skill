# 开源三分流：O1 / O2 / O3

## 路由判定

| 命中条件 | 走哪条 |
|---|---|
| 目标是闭源样本，但疑似基于某个开源卡密/授权/外挂项目（类名、资源、字符串雷同） | **O1** 对照开源实现辅助逆向 |
| 目标本身就是开源项目（给了仓库地址 / 源码目录 / 明确说"这是开源的"） | **O2** 对开源项目本身做分析与改造 |
| 逆向完成后要把成果沉淀下来（还原算法、去混淆代码、Hook 模块） | **O3** 还原产出开源化 |

同一任务可串行走多条：O1 → 定位 → 绕过 → O3 沉淀。

## O1 — 对照开源实现辅助逆向

**目标**：用开源源码当"参考答案"，把黑盒还原变成对照阅读，节省大量试错。

流程：
1. 从样本里提取可用于比对的锚点：
   - 包名 / 类名结构、资源文件名、布局 id
   - 特征字符串、错误提示文案（中文提示尤其好用）
   - 第三方库依赖（`okhttp`、`retrofit`、`MMKV`、特定 SDK）
   - 验证域名、接口路径
2. 用锚点定位到对应开源项目与**版本**（版本必须对齐，否则行号与逻辑对不上）。
3. 对照关系建立后做三件事：
   - 用开源源码的**结构**指导反编译代码的命名与分块
   - 用开源源码的**算法**验证还原出的卡密算法是否一致
   - 用开源源码的**判定点**缩小动态验证范围
4. 结论必须区分：与开源一致的部分（可复用）/ 二次开发改动的部分（需单独逆向）。

**注意**：开源对照是加速器，不是证据。还原结论仍要在目标样本上动态验证。

## O2 — 对开源项目本身做分析

流程：
1. 通读授权相关模块：入口 Activity/Form → 校验 service/函数 → 存储 → 网络。
2. 找薄弱点清单（按代价排序）：
   - 本地常量密钥 / 硬编码 salt
   - 校验只在客户端做，服务端不复核
   - 响应未验签，可改 JSON
   - 到期时间写在本地可改的存储里
   - 算法可逆（可推 keygen）
3. 给出改造方案：patch 判定 / 自建校验替代 / 部署自己的授权服务端（若支持改接口地址）。
4. 交付：diff 补丁 + 编译运行步骤；若改服务端地址，说明如何指向自建服务。

## O3 — 还原产出开源化

把成果整理成可复用代码包：

```
<project>-kami/
├── README.md            # 目标、适用版本、结论、使用方法、边界
├── analysis/
│   ├── protection.md    # 壳与保护分析
│   ├── architecture.md  # A/B/C/D 分类与证据
│   └── keypoints.md     # 判定点清单（文件:位置 + 证据）
├── algorithm/           # 还原出的卡密算法（含单测与样例）
├── hooks/               # Xposed / hook 脚本（可选）
├── patches/             # smali diff / 二进制补丁说明与偏移
└── tools/               # keygen / mock server / 辅助脚本
```

要求：
- README 写清**适用版本与失效条件**，避免误用到别的版本。
- 清理样本中的个人信息、真实服务端凭证、设备标识。
- 算法自带单测：给 2~3 组真实可用的输入输出样例；样例必须来自真实验证，不能编造。
- 不打包原始目标二进制（版权与体积考虑），只留路径说明与哈希。

## 与常规流程的衔接

```
S1 壳分析 ─→ 判定是否开源 ─→ O1/O2 分支 ─→ S1 定位
                                              ↓
                                     S2 出方案（GATE 确认）
                                              ↓
                                     S3 实施 ─→ O3 沉淀产出
```
