# 工程纪律（提炼自 mattpocock/skills）

> 来源：`https://github.com/mattpocock/skills`（MIT）。那是一套**面向软件工程**的 Agent 技能库（TDD、领域建模、code review、grilling 访谈、spec/tickets），**不含任何逆向内容**——因此不整体搬入，只提炼其中可迁移到逆向任务的方法论。

## 一、严格诊断循环（来自 `diagnosing-bugs`）

原方法：`复现为红 → 最小化 → 提出假设 → 插桩 → 修复 → 回归测试`。

映射到逆向：

| 阶段 | 逆向中的对应动作 |
|---|---|
| 复现为红 | 先记录**原版行为**（原 APK 能装 / 原判定点返回 false / 原 exe 报某错） |
| 最小化 | 用最小输入触发：只改一个判定点、只跑一次验证接口 |
| 提出假设 | 登记 `E#`：我认为 X 处是判定点，依据 Y |
| 插桩 | 在判定点加日志/断点/console.log，观察真实参数与返回值 |
| 修复 | 只改被证据确认的那一处 |
| 回归 | 重跑三态 / 重跑产物自检，确认没改坏其它路径 |

**禁止跳过"复现为红"**：没记录原版行为就没法证明补丁是否起作用。

## 二、交付双审（来自 `code-review` 的 Standards + Spec 双维）

原方法：审查分两个独立维度——**Standards**（是否符合规范）与 **Spec**（是否忠实实现原始需求）。

映射到交付前自检：

- **Standards 审**：产物是否合规？
  对齐 OK、签名 OK、dex/manifest 完整、无死代码、寄存器不越界 → `verify_patch.py` + `zipalign4.py check`
- **Spec 审**：是否真的解决了用户要的问题？
  用户要"绕过卡密"，交付的是否真的绕过了？是否只做了"装得上"就宣称成功？是否漏掉了用户明确提的约束（如"不能用 Frida""不要联网打真实服务端"）

**两维都过才算交付**，缺一维即为未完成。只过 Standards 是"技术上没毛刺但方向跑偏"，这是最常见的交付事故。

## 三、先问清再动手（来自 `grill-me` / `grilling`）

原方法：围绕计划持续追问，直到决策树关键分支全部解决。

映射到逆向：

- 只给了路径没说清目标 → 问一句"目标是 A 类本地校验还是要连带处理服务端？"
- 说"破解成功"但没定义成功 → 问清"交付标准是能装、还是能跑、还是功能可用？"
- 关键约束缺失（有没有设备 / 能不能联网 / 架构是 arm 还是 x86）→ 先确认，否则做出来的东西无法验证

**一问胜过十次盲试**。歧义未消除前不动手。

## 四、对照实验（来自 `tdd` 的 red-green-refactor 思想）

原方法：先写一个失败的测试，再让它通过。

映射到逆向：把"补丁生效"当成一个需要被测试的命题。

```
red  ：原版产物 + 原始判定点 → 记录它如何失败（这才是有效对照组）
green：应用补丁 → 同一条件下行为改变
refactor：确认没改坏其它功能（回归）
```

没有 red 阶段的 green 是自欺欺人（可能是补丁根本没生效，而是环境变了）。

## 五、如何取用这套技能本身

若需要完整方法论（写 spec、TDD、重构、领域建模），可安装：

```bash
# Claude Code 插件
claude plugins install mattpocock-skills
# 或可编辑安装（Codex 等）
npx skills@latest add mattpocock/skills
```

对本 Skill 的价值：**它的 27 个 skill 一个都不用装**，只需要上面这四条纪律。逆向任务的主战场仍然是 `references/` 下的实操文档与 `scripts/` 下的工具。
